Scope clarification
This PRD covers the Agent-Friendly API (AFA) layer only — structured, machine-readable HTTP interfaces that allow external AI agent frameworks (Claude CoWork, OpenAI Agents SDK, LangChain, etc.) to operate the portal autonomously. It does not specify a Copilot UI, an MCP server, or bundled first-party agents. Those remain separate roadmap items.


1.  Executive Summary
Today the NeoStrike Operator Portal is a human-facing web GUI. Operators log in, read dashboards, investigate alerts, and take action. This model assumes constant human attention — a constraint that limits operating leverage as operator businesses scale.

F13-AFA adds a parallel interface to the same platform. Every capability exposed in the Tenant Portal — metrics retrieval, alert querying, risk-profile analysis, pre-authorised interventions — is also accessible via a structured, machine-readable HTTP API designed for consumption by autonomous AI agents.

This means an operator can configure AI agents (using any agent framework: Claude CoWork, OpenAI Agents SDK, LangChain, or custom-built) to handle routine daily operations. The leadership team sets policy boundaries once. Agents operate within those boundaries continuously, escalating only when human judgment is genuinely required.

Business framing
The Operator Portal remains unchanged for human users. AFA is an additive layer — same data, same action permissions, same trust model — but exposed through an interface that agents can consume programmatically. No backend logic is duplicated.

2.  Problem Statement
2.1  The daily operations gap
Operator teams currently perform repetitive, structured tasks manually: pulling GGR reports, scanning RG alert queues, reviewing transaction anomalies, issuing welfare outreach. These tasks follow deterministic rules already encoded in the NeoStrike platform. Human operators are redundant for the detection step — they are only genuinely needed for edge-case judgment.

2.2  Current API design is not agent-friendly
NeoStrike’s existing REST APIs were designed for the portal frontend — a human-readable interface. They exhibit characteristics that make autonomous agent operation unreliable:

	•	Errors return free-text messages that agents cannot programmatically act on
	•	No machine-readable capability manifest — agents cannot self-configure
	•	No structured recommended-action field — agents must reason about raw data
	•	Auth is session-based (human SSO) — no policy-scoped agent token model
	•	No event push — agents must poll, creating noise and latency

2.3  Target state
An operator’s leadership team should be able to configure a set of AI agents, grant them scoped credentials, and trust that the platform will execute pre-authorised operations with full audit logging — while escalating anything outside policy for human review.


3.  Goals and Non-Goals
3.1  Goals
	•	Enable any standards-compliant AI agent framework to authenticate, discover capabilities, and operate the portal via HTTP APIs.
	•	Provide machine-readable, semantically structured responses that agents can act on without LLM interpretation of free text.
	•	Implement a three-tier trust model (Observe / Pre-authorised / Human-gated) enforced at the API gateway level.
	•	Provide an Analysis API endpoint that returns structured AI-generated diagnoses of alerts and anomalies, keeping domain reasoning centralised in NeoStrike.
	•	Support real-time push notifications (webhook + SSE) so agents are event-driven, not poll-driven.
	•	Guarantee full audit logging of every agent action under the existing 7-year immutable retention regime.
	•	Publish a capability manifest and OpenAPI 3.1 schema so agents self-configure without bespoke integration work.

3.2  Non-Goals
	•	Building a Copilot UI (natural language chat over portal data) — separate roadmap item
	•	Building an MCP server at the backend — not required for agent interoperability
	•	Shipping first-party bundled agents — those are a layer above AFA
	•	Replacing or modifying the human-facing Tenant Portal web GUI
	•	Autonomous action without operator-defined policy scopes — all agent actions require pre-authorisation

4.  Architecture Overview
AFA is a gateway and API surface layer. It sits in front of the existing NeoStrike platform, translating agent requests into internal service calls and returning structured, semantically rich responses. No core platform logic is moved or duplicated.

4.2  What makes an API agent-friendly
Five design principles distinguish AFA endpoints from the existing portal REST APIs:

1.  Semantic HTTP responses.  Every error includes a machine-readable error_code, error_category, and suggested_action field. Agents can branch on these without LLM interpretation.

2.  Agent discovery manifest.  A /.well-known/agent.json file declares all capabilities, required scopes, rate limits, and policy tier mappings. Agent frameworks can self-configure from this file.

3.  Policy-scoped agent auth.  Agent JWTs carry a policy_scope claim array (e.g. ["metrics:read", "alerts:read", "player:restrict:pre-auth"]) that maps directly to the T1/T2/T3 trust tiers. The gateway enforces scope at request time.

4.  Built-in Analysis API.  Agents call POST /v1/ops/analysis/alerts/{id} to receive a structured AI diagnosis. NeoStrike holds the domain model; the agent does not need to reason about raw RG scores or transaction patterns itself.

5.  Async event push.  Agents subscribe to alert streams. The platform pushes events to agent webhook endpoints or SSE connections when they occur, eliminating polling latency and noise.


5.  Three-Tier Trust Model
All agent operations are governed by a three-tier trust model. Operators configure each agent’s tier at token-issuance time. The gateway enforces the tier on every request.

All T2 and T3 operations are recorded in the existing F11 immutable audit log with agent_id, policy_scope, and execution_timestamp. For UKGC and MGA compliance: T2 actions are treated as pre-authorised operator instructions; T3 actions require an identifiable human approver recorded in the audit trail.

7.  Agent Discovery Layer
Agent frameworks need to discover what a platform can do before they can operate it. AFA publishes two self-describing surfaces:

7.1  Capability manifest  (/.well-known/agent.json)
A JSON document at the well-known path that agent frameworks check automatically. It declares: platform identity, available API domains, required scope strings per action, rate limits, trust tier mapping, webhook event types, and a link to the OpenAPI schema. Claude CoWork and OpenAI-compatible agents that support Agent Capability Discovery will self-configure from this file without bespoke integration.

7.2  OpenAPI 3.1 schema  (GET /v1/ops/openapi.json)
A complete, machine-readable API schema for all AFA endpoints. Includes full request/response type definitions, error codes, scope annotations, and example payloads. Agents using tool-calling frameworks can generate function definitions from this schema automatically. This schema is generated from code — not written manually — and is always in sync with the implementation.

8.  Authentication and Token Model
8.1  Agent JWT
Agent tokens are distinct from human session tokens. They are issued via a dedicated endpoint (POST /v1/auth/agent-tokens) by Super Admin or Compliance Officer role holders. Each token carries:

	•	agent_id — stable identifier for the agent (used in audit log)
	•	tenant_id — operator tenant the agent operates on behalf of
	•	policy_scope[] — explicit list of permitted scope strings
	•	issued_at and expires_at — all agent tokens expire; maximum TTL is configurable per operator
	•	issuer_id — human operator who issued the token (for accountability)

8.2  Token lifecycle
	•	Tokens can be revoked immediately from Settings > Agent Tokens in the Tenant Portal
	•	Token creation, use, and revocation events are written to the audit log
	•	Failed authentication attempts return 401 or 403 with machine-readable error codes and are logged
	•	Rate limits are applied per agent_id, not per IP

Design principle
Agents must never receive a plain English error message as their only signal. Every error an agent might encounter during normal operation must have an error_code constant. The suggested_action field tells the agent its next step without requiring LLM inference.

10.  Async Push — Webhooks and SSE
10.1  Webhook subscriptions
Agents register a callback URL and a list of event types. When a qualifying event occurs, NeoStrike POSTs a signed JSON payload to the callback URL within 500ms of event creation. Delivery is at-least-once with exponential backoff on failure (3 retries over 10 minutes). Each payload includes an event_id for idempotency.

Supported event types: rg_alert_created, rg_alert_escalated, transaction_anomaly_detected, welfare_outreach_triggered, compliance_deadline_approaching, player_risk_score_changed, gamstop_match_detected, bonus_integrity_flag_raised.

10.2  Server-sent events (SSE)
For agents running in environments that cannot accept inbound webhooks, AFA provides a persistent SSE stream at GET /v1/ops/events/stream. The connection stays open and events are pushed in real time. SSE connections authenticate with the agent JWT in the Authorization header.

12.  Operator Configuration  (Tenant Portal — Settings)
Operators configure AFA entirely from the existing Tenant Portal. No engineering access is required. The Settings module gains an Agent Tokens sub-section with the following capabilities:

	•	Issue agent tokens: set agent_id label, assign policy_scope[], set TTL, optionally restrict to IP ranges
	•	View active agent tokens: see last_used, request_count, scope summary
	•	Revoke tokens instantly: immediate effect, revocation event written to audit log
	•	View agent activity: last 30 days of agent_id action summary with drill-down to audit records
	•	Configure T2 policy bounds: per action type, set the thresholds within which T2 pre-authorisation applies
	•	Webhook management: register, test, and revoke webhook endpoints from the portal UI

14.  Acceptance Criteria
14.1  Discovery and auth
	•	GET /.well-known/agent.json returns a valid capability manifest within 100ms with no authentication required
	•	GET /v1/ops/openapi.json returns a valid OpenAPI 3.1 document covering all AFA endpoints
	•	POST /v1/auth/agent-tokens issues a signed JWT containing the specified policy_scope[] within 200ms
	•	A token with metrics:read scope cannot call an Actions API endpoint — gateway returns 403 with SCOPE_INSUFFICIENT

14.2  Metrics and Alerts APIs
	•	All Metrics API endpoints return within the 100ms SLA (Upstash Redis cache)
	•	GET /v1/ops/alerts supports cursor-based pagination and returns correct results for all filter combinations
	•	Webhook events are delivered within 500ms of the trigger event for registered subscriptions
	•	SSE stream delivers events in real time and reconnects automatically on connection drop

14.3  Analysis API
	•	POST /v1/ops/analysis/alerts/{id} returns a typed response (no raw LLM prose) within 5 seconds at p95
	•	Responses always include all required fields: severity, likely_cause, recommended_actions[], confidence
	•	Analysis calls are logged with analysis_type, agent_id, and processing_latency_ms

14.4  Actions API
	•	T2 actions execute synchronously, write to audit log, and return 200 with execution_id within 500ms
	•	T3 actions create a pending_approval record, return 202 Accepted, and appear in the Tenant Portal welfare queue within 1 second
	•	T3 actions do not execute until a human approver clicks approve in the portal
	•	A T2 action that would exceed the operator-configured policy bound is rejected with POLICY_LIMIT_EXCEEDED before execution

14.5  Operator tooling
	•	Super Admin can issue, view, and revoke agent tokens from Settings > Agent Tokens without engineering support
	•	T2 policy bounds are configurable per action type from the Tenant Portal
	•	Agent action history is visible in the Compliance module with full audit detail

15.  Out of Scope for This PRD
	•	First-party bundled agents (GGR Monitor, Player Protection Agent, Bonus Integrity Agent, Compliance Agent)
	•	Natural language / Copilot interface — separate roadmap item
	•	MCP server protocol support — not required; AFA uses standard HTTP/OpenAPI
	•	Multi-tenant agent federation — single-tenant only in v1
	•	Agent-to-agent communication
